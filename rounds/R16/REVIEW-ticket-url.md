## 결함

### D1 · 중간 · 무인증으로 감사 로그를 끝없이 불릴 수 있다

**재현** (사본, 인증 켠 임시 서버, 쿠키·토큰 없음):

```python
fake = f"{int(time.time())+600}.{'0'*12}.{'0'*32}"     # 꼴만 맞는 가짜 티켓
for i in range(500):
    GET f"/app/~{fake}/x/{'A'*200}{i}"                  # 경로 끝만 바꾼다
```

실측: `500 요청 → 403 500번, access.log 500줄, 153,390 바이트 (307 B/요청), 0.88초`.
같은 식으로 `Authorization: Bearer nope` + `/api/x{i}` → **+500줄** (`token-bad`),
`Cookie: theme=dark` + `/api/x{i}` → **+500줄** (`session-bad`).

**무엇이 잘못됐나**
- 티켓 경로는 게이트를 인증 없이 지나가고(`_auth_gate`, 의도된 동작), 라우팅에서 실패하면 `_audit_denied` 를 부릅니다. `token-bad`·`session-bad` 는 게이트의 `_subject()` 안에서 부릅니다. 셋 다 **인증 전**입니다.
- 억제 키가 `(event, subject, path, method)` 입니다. 무인증이면 subject 는 늘 `-` 이고 **경로는 공격자가 마음대로 정합니다**. 그래서 요청마다 새 키가 생기고 한 줄씩 적힙니다. 상한 256 은 `_revoked_last` 사전의 메모리만 묶을 뿐 쓰기는 막지 못합니다.
- `.aimem/access.log` 는 순환·상한이 없습니다. 루프백에서 클라이언트 하나가 약 570 요청/초 → 약 170 KB/s, **하루 약 15 GB** 입니다. 실패 지연(`LoginGuard`)은 이 길에 걸리지 않습니다.
- 그 결과 `aimem_monitor admin audit`(`admin.py:299` `audit_tail`)이 파일 전체를 `read_text()` 로 읽어서, 커지면 관리 도구부터 멈춥니다. 진짜 거절 줄도 홍수에 묻힙니다.
- T-206 전에는 이 세 거절이 감사에 남지 않았으므로 **이번 라운드가 새로 연 공격면**입니다.

**고칠 방향** (하나 이상)
1. 무인증 거절(`subject is None`)은 억제 키에서 **경로를 빼고** `(event, method)` + **전역 속도 상한**(예: 이벤트당 분당 N줄, 넘치면 `생략 N건` 누적)으로 묶습니다. 경로로 억제를 나누는 것은 subject 가 있는(이미 인증된 적 있는) `github-revoked`·주체 불일치에만 둡니다.
2. 또는 감사 쓰기 전체에 프로세스 전역 토큰 버킷을 둡니다(초당 몇 줄, 넘친 수는 다음 줄에 적음).
3. `access.log` 크기 상한/순환을 둡니다(예: 10 MB 넘으면 `.1` 로 돌림). `audit_tail` 은 끝에서 거꾸로 읽게 바꿉니다.

### D2 · 낮음 · `session-bad` 가 세션 쿠키가 없어도 찍힌다

**재현**: 인증 켠 서버에 `Cookie: theme=dark` 로 `GET /api/authinfo` → access.log 에 `session-bad  127.0.0.1  -  GET /api/authinfo 서명·만료`.

**무엇이 잘못됐나**: 조건이 `self.headers.get("Cookie") is not None` 이라서 **아무 쿠키나** 있으면 찍힙니다. 쿠키는 포트로 격리되지 않으므로, 같은 호스트(127.0.0.1·같은 도메인)의 다른 서비스가 심은 쿠키만 있어도 로그인 화면을 열 때마다 "서명·만료" 로 남습니다. 사실과 다른 사유입니다. D1 의 홍수도 여기를 탑니다.

**고칠 방향**: `self._cookie(SESSION_COOKIE) is not None` 일 때만 `session-bad` 를 남깁니다.

### D3 · 낮음 · 억제 표를 일부러 밀어내면 정상 폴링의 억제가 풀린다 (ip 를 뺀 키의 부작용 포함)

**재현**: 서명이 틀린(옛 토큰으로 서명된) 쿠키로 `/api/state` 를 100번 → **1줄**(억제 정상). 이어 `Bearer nope` 로 서로 다른 경로 300개 → 같은 옛 쿠키로 `/api/state` 5번 → **+1줄**. 상한 256 의 LRU 가 정상 키를 밀어냈습니다.

**무엇이 잘못됐나**: 무인증 공격자가 억제 표를 마음대로 비울 수 있습니다. 반대로, ip 를 키에서 뺐기 때문에 미끼 IP 가 59초마다 같은 (event, path) 를 한 번씩 치면 그 키가 계속 살아 있습니다. 그러면 다른 IP 에서 오는 같은 거절은 **IP 없이 `생략 N건` 숫자로만** 남습니다. 건수는 보존되므로 낮음입니다.

**고칠 방향**: D1 의 1번(무인증 거절을 경로로 나누지 않음)을 하면 표를 밀어낼 수단이 사라집니다. 생략된 동안의 **서로 다른 IP 수**(또는 앞 몇 개)를 `생략 N건(ip k개)` 처럼 싣으면 미끼 문제도 줄어듭니다.

### D4 · 낮음 · 무인증 요청마다 허용 목록 읽기 + HMAC N번

**재현** (`app_ticket_resolve` 를 직접 부름, 일치 없음):

| 허용 목록 크기 | 요청당 resolve |
|---|---|
| 10 | 0.04 ms |
| 1,000 | 3.53 ms |
| 10,000 | 39.72 ms |

HTTP 로 재면 허용 목록 1,001줄일 때 유효 티켓 7.59 ms, 위조 티켓(무인증) 6.78 ms 입니다.

**무엇이 잘못됐나**: 가짜 티켓(꼴만 맞음)을 든 무인증 요청 하나가 파일 읽기 + (N+2)번 HMAC 을 시킵니다. 현실적인 목록(수십 줄)에서는 무시할 만하지만, 목록이 크면 무인증 CPU 증폭이 됩니다. 앱 하위 자원마다 반복되는 정상 비용이기도 합니다.

**고칠 방향**: `(허용 목록 파일 mtime_ns·size·inode, key)` 를 열쇠로 `{tag: subject}` 사전을 캐시합니다. 요청마다 `stat` 은 하므로 **회수는 여전히 즉시** 듣고, 조회는 O(1) 이 됩니다.

## 정보 (결함 아님 - 확인한 것)

- **I1 타이밍.** 태그 비교는 `hmac.compare_digest` 입니다. 이른 반환은 **일치했을 때만** 있습니다. 공격자는 키 없이 특정 로그인의 태그를 만들 수 없고, 후보 순서는 `set` 순회라 프로세스마다 무작위입니다 → **로그인 존재 여부가 새지 않습니다.** 위조 티켓의 응답 시간은 늘 "전부 순회" 입니다. (M19 `==` 바꿈은 시험으로 잡을 수 없는 성격이라 구멍으로 치지 않습니다.)
- **I2 태그 48비트.** 충돌을 강제로 만들어 보면(`gh:alice`·`gh:bob` 같은 태그) bob 의 티켓이 `gh:alice` 로 풀리고, 이어 `app_ticket_ok` 의 mac(주체 포함)이 **거절**합니다 → 다른 주체로는 열리지 않고 닫힌 쪽 실패입니다. 로그인 1,000개에서 충돌 확률은 1.8e-9 이라 충분합니다. 덧붙이면, 태그는 토큰을 갈기 전까지 주체마다 **고정된 가명**이라 URL(방문 기록·화면 공유) 사이에서 같은 사람임을 이을 수 있습니다. 로그인 자체는 새지 않습니다.
- **I3 회수 실패 방향.** 허용 목록이 `chmod 000` / 주석·빈 줄만 / 없음 / 디렉터리 / BOM 붙은 `kim` 일 때 모두 gh 티켓 → **403**, 토큰 티켓 → 200, 되돌리면 → 200. 열리는 길은 없습니다. (BOM 이면 정당한 `kim` 도 막힙니다. `github_allowed_logins` 의 기존 동작이고 닫힌 쪽입니다.)
- **I4 `app_ticket_ok` 의 태그 비교(M6)는 동치 변이**입니다. 지워도 mac 이 주체를 묶고 resolve 가 태그를 이미 봅니다. 빨개지지 않는 것이 맞습니다.
- **I5 사소.** `log_line("\n내립니다.")` 는 시각만 있는 빈 줄을 하나 더 찍습니다. `_APP_RE` 끝 처리는 이상 없습니다: `/app/~~abc/x/` → 티켓 `~abc`(꼴 거절 403), `/app/%7Ex/` 는 인증 후 404, 161자 티켓은 라우팅되지 않습니다.
