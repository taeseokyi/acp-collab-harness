## 새 결함

### N1 · 중간 · 티켓 URL 하나로 전역 상한을 채워 진짜 거절을 묻는다

**재현** (사본, 인증 켬, 허용 목록 `kim lee park`):

1. kim 이 정상 발급받은 `/app/알파/` 의 티켓 `T` 하나를 얻습니다. URL 에 있으므로 방문 기록·화면 공유·어깨너머로 얻을 수 있고, **만료돼도 됩니다**.
2. 쿠키 없이 `GET /app/~T/베타/z{i}` 를 i=0..299 로 보냅니다. 앱 이름이 달라서 mac 이 틀리고 → `app-ticket-bad gh:kim … 서명·만료` 가 됩니다. 키 `(event, gh:kim, 경로, GET)` 가 요청마다 새로 생깁니다 → **60줄 뒤 상한**.
3. 허용 목록에서 lee 를 지운 뒤 lee 쿠키로 `/api/state`(401)·`/app/알파/`(302) → **감사 0줄**.
4. 만료된 티켓(`exp=now-10`)으로 경로 80개 → 60줄. 만료와 상관없이 같은 길을 탑니다.
5. 지속 공격(가상 시계): 공격자가 매 분 시작에 60줄을 채우고, 회수된 park 가 10초마다 시도 → **30분, 150번 시도, park 줄 0개**. park 의 건수는 공격자 줄의 `생략 N건` 숫자로만 보이고 주체·IP 는 사라집니다.

**무엇이 잘못됐나**
- `has_subject` 가 `ticket_subject` 를 인증된 주체처럼 다룹니다(`server.py:2682`. 2686 은 주체가 `-` 라 해당 없음). 이 값은 **요청자를 인증한 결과가 아니라 URL 에 든 태그를 푼 것**입니다. 그래서 경로가 키에 들어가고, 무인증 요청자가 키를 마음대로 늘립니다. D1 이 이 갈래에서는 열린 채로 남아 있고, 전역 상한이 그것을 "로그 크기 문제" 에서 "감사 누락 문제" 로 바꿨습니다.
- 상한에 걸린 거절도 `_revoked_last[key] = (now, …)` 로 "기록됨" 표시가 됩니다(741-742행이 750행보다 먼저). 그래서 그 키는 이후 60초 동안 키 억제까지 받습니다. 매 분 상한이 차 있으면 영원히 안 남습니다.
- 줄에는 `gh:kim` 이 찍혀 있어 **티켓 주인이 공격자로 보입니다**.
- 회수된 사용자 본인이 세션 쿠키로 경로를 바꿔 가며 보내도 같은 일이 생깁니다(`github-revoked` 는 진짜 인증 주체). 다만 이때는 줄에 자기 이름이 남습니다.

**등급 근거**: 로그인이 필요 없고 문턱은 URL 한 줄입니다. 감사의 목적(회수된 계정의 시도를 남기는 것)을 무력화합니다. 데이터 노출·권한 상승은 없으므로 중간입니다.

**고칠 방향**
1. 티켓에서 푼 주체는 **무인증으로 취급해 키에서 경로를 뺍니다**: `(event, ticket_subject, method)`. 경로를 키에 넣는 것은 `_subject()` 가 인증한 주체(`github-revoked`, 주체 불일치)만 하게 합니다. 이렇게 하면 키 수가 허용 목록 크기 × 이벤트 × 메서드로 묶입니다.
2. 상한을 **몫별로** 나눕니다(예: 무인증 몫·티켓 몫·인증 주체 몫). 아니면 "이번 창에서 처음 보는 `(event, subject)` 는 상한과 무관하게 1줄" 을 보장합니다.
3. 상한에 걸린 경우에는 `_revoked_last` 의 시각을 갱신하지 않습니다(기록되지 않은 것을 기록됨으로 표시하지 않음).

### N2 · 낮음 · `생략 N건` 이 다른 사건의 줄에 실린다 (건수는 보존, 귀속은 틀림)

**재현** (직접 호출, 가상 시계): kim `github-revoked` 1줄 → 같은 키 10번 더(삼킴) → 무관한 `token-bad` 한 번 → 그 줄이 `token-bad  z  -  GET /api/q 생략 10건 토큰 불일치`. 61초 뒤 kim 의 다음 줄은 `GET /api/state r` 로 **생략 표기 없음**.

**무엇이 잘못됐나**: 생략 수가 키별 `rec[1]` 이 아니라 전역 `_denied_key_skipped + _denied_cap_skipped` 입니다. `rec[1]` 은 736행에서 늘리기만 하고 쓰지 않는 죽은 값입니다. 읽는 사람은 "token-bad 가 10번 더 왔다" 고 읽습니다. 또 홍수가 끝나면 남은 숫자(실측 997, 19,940)는 **다음 거절이 올 때까지 어디에도 안 남습니다**.

**고칠 방향**: 키 억제 수는 그 키의 줄에 `rec[1]` 로 싣습니다(T-206 동작). 상한으로 버린 수는 따로 `상한 생략 M건` 으로 적습니다. 창이 바뀔 때 0 이 아니면 `audit-dropped` 한 줄로 털어 냅니다.

### N3 · 낮음 · 무인증 줄의 경로가 처음 본 경로에 고정된다

**재현**: `token-bad` 를 `/api/q` 로 한 번 → 61초 뒤 `/api/REAL-TARGET` 로 → 새 줄의 detail 이 `GET /api/q 토큰 불일치`.

**무엇이 잘못됐나**: 741행 `first_path = rec[2] if rec is not None else safe_path` 가 **창이 지난 뒤에도** 옛 레코드의 경로를 이어받습니다. 무인증 키는 6개뿐이라 밀려나지도 않습니다. 그래서 서버가 떠 있는 동안 그 event 의 줄은 **늘 첫 경로**를 적습니다. 공격자가 먼저 무해한 경로를 한 번 보내 두면 이후 진짜 표적 경로는 감사에 한 번도 안 나옵니다.

**고칠 방향**: 기록할 때는 지금 요청의 `safe_path` 를 씁니다. "억제된 동안 본 경로" 를 싣고 싶으면 따로 몇 개만 모읍니다.

### N4 · 낮음(시험) · D1 회귀 시험이 거짓 초록이고, 전역 상한은 시험이 없다

`test_unauthenticated_flood_is_bounded` 는 `/app/~bad{i}/알파/` 처럼 **티켓 칸만** 바꿉니다. 그런데 `_TICKET_LOG_RE` 가 키를 만들기 전에 그 칸을 `~***` 로 가리므로, 경로를 키에 되돌려도(M21) 키가 하나라서 초록입니다. 앞 검수의 재현처럼 **티켓 뒤 경로**(`/x/A…{i}`)나 `/api/x{i}` 를 바꿔야 합니다. 상한(M22·M24·M26)과 생략 초기화(M25)를 겨눈 시험도 없습니다.

**메울 방향**: (a) 무인증 세 갈래를 각각 경로 꼬리를 바꿔 200번 → ≤ 상수 줄. (b) 키 61개 이상 → 정확히 60줄, 그다음 줄에 생략 수. (c) 시계를 61초 넘긴 뒤 다시 1줄(창 재개). (d) 생략 수가 두 번 실리지 않음. (e) N1 이 고쳐지면 "티켓 하나 + 경로 300 → 줄 ≤ 상수, 이어서 회수된 주체 1줄 남음".
