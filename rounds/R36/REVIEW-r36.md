# R36 적대적 검수 - VoxLog R35-N1·N2·N3 수정 (T-368, S1)

**판정: 통과** - 상 0 · 중 0 · 하 3

R35-N1·N2·N3 은 모두 닫혔습니다. 실제 상수로 잰 값이 공식과 초 단위까지 맞고, 새 검사 4개(단위 3·브라우저 1)는 제가 넣은 변이를 모두 잡았습니다.
남은 것은 하 3건입니다. 서비스 워커 쪽 408 처리를 지키는 검사가 없고, 문서의 요약 한 줄이 옛 내용 그대로이며, 이미 있던 분류 문제(멈춘 업로드가 408 이 아니라 400)가 하나 있습니다.

## 4. 다음 담당자가 알 것

- 세 건 모두 하이고 닫힘 판정에 영향이 없습니다. 큐에 `[VoxLog] R36-N1~N3` 로 넣으면 됩니다. N1·N2 는 각각 몇 줄로 끝납니다. N3 은 serve.py 한 줄과 단위 검사 하나입니다(E5 를 grace 를 줄여 재현).
- R35-N4(최소 속도 16KB/s 가 느린 폰 회선에 높을 수 있음)는 이번 범위가 아니었지만 새 공식에서 성질이 바뀌었습니다. 이제는 **크기와 상관없이** 속도 r < 16KB/s 이면 30·16/(16−r) 초 뒤에 끊깁니다(12KB/s → 120초, 8KB/s → 60초, 15KB/s → 480초). 12KB/s 회선이면 약 1.4MB 까지는 올라갑니다. 판단은 여전히 태석님 몫입니다.
- 408 은 서버가 본문을 다 읽기 전에 닫으므로, 실제 폰에서는 대개 연결 오류('연결 안 됨')로 보입니다. 그러면 queue.js 는 Retry-After 로 다시 시도하지 않고 다음 online·보임·앱 열기·sync 때 올립니다. 문서 187행이 이를 적고 있습니다. 24번은 `route.fulfill` 로 408 을 깨끗하게 넣는 경로만 봅니다.
- PROGRESS.md 20행은 "단위 115·브라우저 23/23" 입니다. 지금은 단위 119·브라우저 24/24 입니다(PROGRESS 는 이 슬롯의 쓰기 범위 밖이라 고치지 않음).
- 저장소에서 쓴 것은 이 파일 하나입니다. `/tmp/r36s1/` 는 지워도 됩니다.
