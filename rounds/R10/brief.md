## 1-1. 결과물은 프로젝트 폴더에, 라운드 폴더에는 기록만
**프로젝트**는 여러 라운드를 묶는 단위입니다. 결과물은 라운드마다 흩어지지 않고 **`projects/<프로젝트>/` 한 곳에 여러 라운드에 걸쳐 쌓입니다.** 요청마다 프로젝트가 붙어 옵니다(`aimem_db.py request list` 의 `[이름]`, 요청 파일의 `project`).
- **시작할 때** 그 프로젝트의 `projects/<프로젝트>/PROGRESS.md` 를 먼저 읽습니다 - 앞선 라운드가 무엇을 만들었고 무엇이 남았는지가 거기 있습니다(당신은 기억이 없습니다). 폴더가 없으면 새 프로젝트이니 만들고 `README.md`(무엇을 만드는 프로젝트인지, 폴더 구조)를 씁니다.
- **목표를 적습니다.** `PROGRESS.md` 맨 위(제목 바로 아래)에 `## 목표` 절을 두고, 이 프로젝트가 "다 됐다" 고 하려면 있어야 할 것을 체크리스트로 적습니다(`- [ ] 로그인 화면`, 끝난 것은 `- [x]`). 새 프로젝트면 요청과 README 를 보고 **끝까지 가는 데 필요한 목표를 예측해서** 5~15개로 씁니다 - 이번 라운드에 할 것만 적지 않습니다. 이어받은 프로젝트면 끝난 것을 체크하고, 새로 드러난 목표는 덧붙이고, 필요 없어진 것은 지우고 그 사실을 라운드 항목에 한 줄 적습니다. 웹의 프로젝트 진행률이 이 체크리스트의 "끝난 수 / 전체" 입니다. 검증까지 끝난 것만 체크합니다.
- **만들 때** 이미 있는 결과물을 이어서 고칩니다. 라운드 번호가 붙은 사본(`v2`, `R10-…`)을 옆에 만들지 않습니다 - 이력은 git 에 있습니다.
- 작업자에게 쓰게 하려면 먼저 `python3 tools/aimem_db.py ownership set --path "projects/<프로젝트>/<하위 경로>/**" --owner S<n> --note "R10"` 로 배정합니다. 같은 파일을 두 슬롯에 주지 않습니다.
- **끝날 때** `## 목표` 의 체크를 실제 상태에 맞추고, 그 절 **바로 아래**에 이번 라운드 항목을 덧붙입니다(라운드 항목끼리는 최신이 위): `## R10 (날짜)` - 한 일, 바뀐 파일, 검증한 방법, **남은 일**. 다음 라운드의 관리자가 이것만 읽고 이어받을 수 있어야 합니다.
- **구분이 화면에 보이게:** 태스크를 만들 때 `aimem_db.py task set --id T-xxx --request <요청 id> …` 로 요청을 꼭 잇고, 그래프 노드에는 `"project": "<프로젝트>"` 를 적습니다(함대 자체 일이면 생략). 식별자(T-/G-)에는 프로젝트·라운드를 붙이지 않습니다 - 실행 기록에 따로 남아 화면이 프로젝트별로 보여 줍니다.
- 요청을 직접 만들 때(작업 중 생긴 후속 일)는 `aimem_db.py request set --id <id> --title … --project <프로젝트>` 로 프로젝트를 붙입니다. 노드의 `"project"` 는 폴더 이름 하나여야 하며 아니면 `fleet_graph new` 가 거절합니다.
- **프로젝트가 비어 있는 요청**은 함대 자체의 일입니다(`tools/`, `tests/`, `AIMEM.md`). 그 파일을 제자리에서 고칩니다.

## 2. 턴 규칙
- 기다릴 때는 `fleet_graph.py run` 을 **포그라운드로 블로킹**합니다. 백그라운드 감시 + "알림 오면 잇겠다" 로 턴을 끝내지 않습니다. 보고를 본문에 다 쓰기 전에는 턴이 끝나지 않습니다.
- 프로세스는 **pid 로만** 죽입니다(`pkill -f` 금지).
- **커밋·푸시 금지.** 커밋은 라운드가 끝난 뒤 클로드 코드가 합니다.
- **큰 출력은 직접 읽지 않습니다.** 작업자 보고는 첫 줄(`DONE|PARTIAL|BLOCKED|NEEDS-*`)과 요약만, 테스트·린터는 `| tail -20` 또는 실패 줄만, diff 는 `git diff --stat` 뒤 해당 hunk 만.
- **유료 모델 대체 금지.** kistillm(S2)·EXAONE(S3) 장애 시 S1/S4 claude 로 옮기지 않고 그 태스크를 BLOCKED 로 두고 보고합니다.
- **함대 모드.** `fleet_graph run` 출력에 `함대 모드: paused|stopped|ready` 가 찍히거나 rc 3 이면 사람이 멈춘 것입니다. 우회하지 말고(`AIMEM_FLEET_FORCE` 금지) 체크포인트를 남긴 뒤 `상태: PARTIAL` 로 보고하고 끝내십시오.
- **모니터는 HTTPS + 인증**입니다. 작업자에게 운영 서버를 `curl` 로 부르게 하지 말고(401), 토큰을 브리프에 넣지 마십시오. 서버 동작은 테스트가 임시 포트에 띄우는 서버로 확인합니다. 서버 코드를 바꿨으면 `tools/aimem_monitor/monitorctl.sh restart`.

## 3. 그래프 짜기
- **라운드 = 그래프 하나(원칙).** 과제 전체를 의존관계(`deps`) 포함 한 그래프로 짭니다. 둘 이상은 앞 그래프 결과로 계획이 바뀌어야 할 때만.
- **검수는 그래프 안의 노드로**(`verify` 는 그 노드 범위). 관리자는 그래프가 끝난 뒤 한 번만 확인합니다.
- **무료 슬롯 우선 - 만드는 일과 고치는 일은 S2·S3 가 합니다.** 새 코드 쓰기·결함 수정·테스트 작성·문서 정합은 S2(kistillm)에 먼저, 넘치면 S3(EXAONE, 동시 1개)에 줍니다. S1·S4(유료)는 **판단·설계·적대적 검수에만** 씁니다 - "빨라서" 는 이유가 아닙니다(작업자는 무료 모델, 느린 것은 그 값입니다. R7 은 아홉 태스크 중 일곱을 유료 슬롯에 줬습니다). 검수가 찾은 결함도 검수한 슬롯이 아니라 S2·S3 가 고칩니다. 유료 슬롯에 만들기·고치기를 줘야 했다면 보고 (6)에 태스크별로 이유를 적습니다. S2 는 한 번에 한 요청을 처리하니 S2 노드끼리는 `deps` 로 줄 세우고, 그 사이 S3·검수 노드를 겹칩니다. S3 에게는 좁은 일을 줍니다(이미 있는 파일에 케이스 추가, 한 함수 수정) - 표나 긴 목록을 옮겨 적게 하지 않고, 읽을 파일·줄 범위를 못박고 "읽지 말 것"도 적습니다.
- **S2(codex)는 샌드박스 안에서 돕니다 - 브라우저를 띄우거나 TCP 소켓을 열지 못합니다**(R8 실측: Chromium `sandbox_host` FATAL, 소켓 `PermissionError`). 브라우저·로컬 서버가 필요한 스크립트를 S2 에게 쓰게 할 수는 있지만 S2 는 그것을 돌려 보지 못합니다. 그런 노드는 `verify` 에 그 스크립트 실행을 걸어 엔진이 샌드박스 밖에서 돌리게 하고, 브리프에 "직접 실행은 안 되니 문법 확인까지만 하고, 실행 결과는 verify 가 본다. 재시도 때 verify 출력 꼬리를 보고 고친다" 고 적습니다. 스크립트는 마지막 줄들에 실패 원인이 찍히게 짜게 합니다(재시도 브리프에는 verify 출력 꼬리 600자만 갑니다).
- **브라우저·서버를 돌려야 하는 일은 S3 에게 줍니다**(S3 는 Chromium 이 뜹니다 - R8 실측). S2 에게는 돌려 보지 않아도 되는 일을 줍니다.
- **검사를 만드는 노드의 `verify` 는 "검사가 돌았다" 이지 "제품이 통과했다" 가 아닙니다.** 테스트·검증 스크립트를 쓰게 하는 노드에 `verify: 그 스크립트 실행` 을 걸면, 스크립트가 **제품의 진짜 결함**을 찾았을 때 작업자는 할 일을 다 했는데도 노드가 실패하고, 고칠 수 없는 일을 똑같이 한 번 더 한 뒤(R8: T-105·T-106 이 그렇게 8~20분씩 더 썼습니다) 뒤 노드를 전부 막습니다. 그런 노드는 `verify` 를 "스크립트가 끝까지 돌고 요약 줄을 찍는다" 로 겁니다(예: `python3 …/x.py | tail -1 | grep -q '^통과 [0-9]* / 전체'`). 다만 **요약 줄만 보면 작업자가 아무것도 안 해도 통과합니다**(이미 있던 스크립트가 요약 줄을 찍으니까. R9: T-116 이 54초 만에 한 줄도 안 고치고 `done` 이 됐습니다) - `verify` 에 "이번에 더하라고 한 검사 이름이 출력에 있다" 를 같이 겁니다(예: `… > /tmp/o.txt; grep -q '통계 - 진 판 뒤' /tmp/o.txt && tail -1 /tmp/o.txt | grep -q '^통과'`). 가장 간단한 것은 **"검사 수가 지금보다 크다"** 입니다(R9 관리자: `… | tail -1 | python3 -c "import sys; p=sys.stdin.read().split(); sys.exit(0 if len(p)==5 and int(p[4])>=65 else 1)"`) - 제품의 통과 여부와 무관해서 검사가 결함을 찾아도 노드가 막히지 않고, 아무것도 안 한 시도는 통과하지 못합니다. 결함 수정 노드에는 `통과 수 == 전체 수` 를 함께 겁니다. (엔진도 보고가 도구 호출 글자로 끝난 시도와, 쓰라고 받은 경로를 하나도 안 고친 첫 시도를 실패로 봅니다 - 로그의 `aborted`·`no-op`.) 그리고 노드가 유난히 빨리 끝났으면(무료 슬롯이 2분 안쪽) 파일이 실제로 바뀌었는지 `git status`·수정 시각으로 확인합니다. 찾은 결함은 작업자가 보고에 적고, 그것을 고치는 노드와 "이제 전부 통과한다" 를 `verify` 로 거는 재검증 노드를 뒤에 따로 둡니다. 작업자 브리프에는 "검사가 제품 결함 때문에 실패하면 제품도 검사도 고치지 말고 첫 줄을 `NEEDS-FIX: <무엇이 어디서>` 로 보고하라" 고 적습니다 - 엔진이 재시도 없이 바로 막힘으로 두므로 당신이 곧바로 고치는 노드를 붙일 수 있습니다.
- **화면 검사는 속성·클래스가 아니라 실제로 그려진 것을 묻습니다**(R8 관리자 개선안: 속성만 본 검사 31개가 초록인 채 화면 결함 다섯이 숨어 있었습니다). `hidden`/`display` → `is_visible()`, 색 → `getComputedStyle`, 자리·겹침·잘림 → `bounding_box()`. 속성은 곁들여 볼 뿐 그것만으로는 증거가 아닙니다. 화면이 있는 프로젝트는 "요소끼리 겹치지 않는다" 와 "입력한 뒤에도 화면 밖으로 안 나간다" 검사를 처음부터 넣습니다. 화면 태스크 브리프에 이 규칙을 옮겨 적습니다.
- 막힌 노드는 원인을 확인한 뒤 `fleet_graph.py unblock <그래프> <노드>` 로 다시 굴립니다(작업자가 살아 있으면 거절됩니다).
- 핸드오프는 `8.0-8` 종료 1번대로 `handoff add --bump --expect-rev N`.
