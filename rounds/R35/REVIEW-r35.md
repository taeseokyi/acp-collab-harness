# R35 적대적 검수: R34-N4·N6·저장 OSError 처리 (S1, T-364)

**판정: 조건부 통과. 상 0 · 중 0 · 하 4.** 막는 결함은 없습니다.
- R34-N4 는 닫혔습니다. 문서에 적혔고, 실제 서버로 503 을 받는 검사 22번이 생겼으며, 변이 2개를 모두 잡았습니다.
- 저장 OSError 처리도 닫혔지만, 남은 구멍이 하나 있습니다(R35-N3).
- R34-N6 은 이제 끝이 있는 문제가 되었습니다. 다만 마감이 **선언된** 길이로 계산되므로, 50MB 를 선언하고 아주 느리게 보내는 연결이 업로드 자리를 최대 3230초(54분) 동안 쥘 수 있습니다(R35-N1).

## 2. 실측

### (1) 느린 연결 (exp2: 클라이언트가 계속 recv 하면서 응답이 온 시각을 잼)

| 실험 | 결과 |
|---|---|
| A: 491520B 선언(마감 60초), 59초마다 1바이트 | **408, 60.0초** |
| B: 헤더만 보내고 멈춤(5MB 선언) | 400, 60.1초 (recv 1회 timeout 60 → `cut`) |
| C: 100KB 보낸 뒤 멈춤(5MB 선언) | 400, 60.1초 |
| D: **50MB 선언**, 59초마다 1바이트 | 130초에 클라이언트가 스스로 닫을 때까지 응답 없음. 그동안 자리를 쥠(`남은 자리 9/10`), 닫힌 뒤에야 400 로그. 계산상 마감은 `30 + 52428800/16384 = 3230초` |

exp.py 의 E1~E3 시각(177/75/75초)은 클라이언트가 보내기를 다 마친 뒤에 잰 값이라 버리고, 위 exp2 값을 씁니다.

### (2) 큰 정상 업로드

| 실험 | 결과 |
|---|---|
| E4: 2MB 를 20KB/s 로 (마감 158초) | 201, 102.4초 |
| E5: 2MB 를 12KB/s 로 (마감 158초, 다 보내려면 171초) | **408, 158.7초**. 클라이언트에는 `BrokenPipeError` 로 보임 |

계산:
- 50MB 를 정확히 16KB/s 로 보내면 3200초가 걸리고 마감은 3230초라 통과합니다. 여유는 30초뿐입니다.
- 16KB/s 보다 조금이라도 느리면, 0.5MB 를 넘는 파일은 모두 408 을 받습니다(R35-N4).

### (3) 408/500/507 뒤의 상태

| 실험 | 결과 |

모든 실험 뒤 상태:

- 정리·자리·전사기 상태는 올바릅니다.

### (4) 페이지 대기열 (`web/queue.js:241`·`249`)

- 408·500·507 은 영구 실패(`perm` = 400·413·415)가 아닙니다. 그래서 `waiting` 으로 남습니다.
- 500·507 은 `>= 500` 이라 `scheduleRetry` 를 겁니다.
- 408 은 `>= 500` 이 아니어서 `return next()` 로 다음 줄로 넘어가고, 다시 시도를 걸지 않습니다. 다음 online·보임·새 녹음 때 다시 올라갑니다. 서비스 워커(`web/sw.js:181`)도 같습니다.
- 영구 실패로 가지 않으니 대상 요건은 맞습니다. 하지만 문서와 어긋납니다(R35-N2).
- 408 처리를 지키는 검사가 없습니다. `grep -rn 408 projects/VoxLog` 결과에 web·브라우저 검사는 없습니다.

### (5) 검사 22번

- 실제 `serve.py` 프로세스에 원시 소켓 둘로 자리를 채운 뒤, 페이지가 실제 503 과 `Retry-After 5` 를 받습니다(출력으로 확인).
- 변이 A·B 를 모두 잡습니다.
- 사소한 점: 출력 문구가 `"503 문구 수신(status %s…"` 로 고정되어 있어, 변이 A 에서는 `503 문구 수신(status 400…)` 으로 찍힙니다. 판정에는 영향이 없습니다.

### (6) 문서 대조

- 상수, 마감 공식, 408·500·507 문구, ENOSPC/EDQUOT→507, `make_server` 인자, 503/507 이 연결 오류로 보일 수 있다는 서술은 코드와 맞습니다.
- 어긋나는 곳은 184행의 408 서술입니다(R35-N2).

## 4. 대상별 닫힘 판정

- **R34-N4: 닫힘.**
  - 문서 163행 부근에 "503/507 이 연결 오류로 보일 수 있음" 이 적혔습니다.
  - 검사 22번이 실제 서버의 503 을 거칩니다(Playwright 응답에 status 503, Retry-After 5).
  - 변이 A(503→400)·B(503 을 perm 으로)를 모두 잡습니다.
- **R34-N6: 조건부 닫힘.**
  - 59초마다 1바이트·헤더만·조각 사이 멈춤 모두 60초 안팎에 자리를 놓습니다(408/400 각 60.0~60.1초).
  - 정상 2MB 20KB/s 는 201 입니다.
  - 다만 마감이 선언 길이에 비례해서, 큰 선언이면 최대 54분까지 쥘 수 있습니다(R35-N1). 하 등급이라 이번 라운드를 막지는 않습니다.
- **저장 OSError 처리: 닫힘(구멍 하나는 R35-N3).**
  - incoming 쓰기 EACCES→500, fsync ENOSPC→507, `os.replace` EIO→500, 메타 ENOSPC→507 모두 `Connection: close` 로 답했습니다. 뒤이어 같은 cid 로 201, incoming 은 비어 있고, `_inflight`·`_reserved_rids` 도 비었습니다.
  - 끊긴 쪽에 답할 때(E10·E11) 트레이스백이 없습니다.

## 5. 다음 담당자가 알 것

- 실험 스크립트는 `/tmp/s1r35/exp.py`·`exp2.py`, 변이 사본은 `/tmp/s1r35/mutA`·`mutB`·`mutC` 입니다. mutC(408 을 perm 으로)는 돌리지 않았습니다. 408 을 보는 검사가 없어 잡히지 않을 것이 grep 으로 확실하기 때문입니다.
- 느린 연결 실험은 실제 상수라 약 3분 걸립니다. 단위 검사(`test_slow_upload_408_frees_slot`)는 grace 1, rate 1e9 로 줄여 1초 마감을 씁니다.
- TLS(`--tls`) 경로에서는 재지 않았습니다. `self.connection.settimeout` 은 SSLSocket 에도 적용되지만, TLS 읽기 오류(`ssl.SSLError`)는 OSError 갈래로 가서 500 을 쓰려 합니다. 이때 끊긴 TLS 소켓이면 `_upload_err` 가 SSLError 를 잡지 못해 트레이스백이 날 수 있습니다(코드 경로상 추정, 실측 안 함).
