아이디어 번호 `I1`~`I6`. 의견 단계(G-101)에서는 자기가 낸 아이디어를 빼고 의견을 냅니다.

## I1 (S2 codex · T-421): 녹취 제목·태그 직접 붙이기
- 근거: 녹음·파일 올리기 뒤 목록과 상세 제목이 모두 자동 받아쓰기 첫 줄(`가짜 받아쓰기 …`)이었고, 상세에 이름을 고치는 칸이나 태그가 없었습니다. 검색은 받아쓴 글과 자동 제목만 찾으므로 회의 이름·상대·주제를 기억해 ASR 문구를 정확히 넣어야 했습니다. STT가 실패하면 제목도 비어 있습니다.
- 이득: 나중에 "주간회의", "A사 통화", "아이디어" 같은 안정된 이름과 태그로 찾고 묶을 수 있습니다. 받아쓰기가 틀리거나 없어도 사용자가 붙인 라벨은 남습니다.
- 구현 범위: 서버(`store.py` 메타에 `label`·`tags`, 수정 API, `list(q)` 검색에 포함) + 화면(상세 편집 칸·목록 표시·태그 검색/거르기) + 저장(기존 `meta/<id>.json`). 대략 중간.
- 기존 구조와 맞음: 이미 있는 `title`, `meta/<id>.json`, `Store.list(q)`의 제목·글 검색, 상세 화면을 그대로 확장합니다. 새 저장소나 색인은 필요 없습니다.

## I2 (S2 codex · T-421): 답에 출처 녹취 목록과 바로 열기
- 근거: 두 녹취를 골라 요약을 묻자 상태는 `요약 · 11/25 00:42 · 녹취 2건`이었지만 답 아래에 출처 목록이 없었고, 지난 답 목록도 첫 녹취 제목에 `외 1건`만 보여 두 번째 녹취를 열 수 없었습니다.
- 이득: 답이 어느 녹취에서 나왔는지 확인하고 해당 녹취의 음성·받아쓴 글로 바로 이동할 수 있습니다. 여러 건을 묶어 묻는 경우 신뢰가 특히 올라갑니다.
- 구현 범위: 서버(`serve.py`가 답 응답에 `ids` 기반 `sources`—제목·시각·상태—를 붙임; 필요하면 `ask.py` 프롬프트에 id 인용 요청) + 화면(답 아래 출처 카드, 클릭 시 기존 상세 열기). 대략 작음~중간.
- 기존 구조와 맞음: `answers/<aid>.json`의 `ids`·`about`, `serve.py`의 답 응답, `web/app.js`의 `openDetail(id)`를 그대로 씁니다.

## I3 (S3 opencode · T-422): 녹취 주제 태그(자동 제안 + 손질)와 태그 거르기
- 근거: 기록 목록의 자동 제목이 받아쓴 글 앞 40자뿐이라 세 녹취가 모두 `가짜 받아쓰기 …` 같은 꼴로 보였고, 회의·통화·짧은 생각을 가려낼 표시가 없었다. 검색은 글 부분일치뿐이라 주제로 모아 볼 수 없었다.
- 이득: 나중에 "그 회의", "그 통화"를 주제 태그로 바로 찾고, 같은 주제의 녹취를 묶어 보고 묻는다.
- 구현 범위: 서버 `meta`에 `tags` 저장과 `list`의 `tag` 필터·묻기 ids 묶음, 화면 목록의 태그 칩과 상세의 태그 편집. 자동 태그는 기존 `run_llm`으로 제안만 하고 저장은 사용자가 확인. 대략 중간.
- 기존 구조와 맞음: `Store`의 meta JSON, `list`의 q/date/status 필터, `ask.build_prompt`의 ids 묶음, `web/app.js` 목록·상세 렌더링을 그대로 확장한다.

## I4 (S3 opencode · T-422): 묻기 답 이어 묻기(대화 실)
- 근거: 요약 답을 받은 뒤 "이 회의에서 정한 일정만"을 직접 묻기 위해 묻기 탭으로 돌아가 같은 녹취를 다시 체크하고 질문을 새로 입력해야 했다. 지난 답은 서로 이어지지 않는 평면 목록이고, 앞 답을 문맥으로 쓸 방법이 없었다.
- 이득: 요약 → 할 일 → "그 일정은 누가 맡나?" 같은 후속 질문을 한 흐름에서 이어 갈 수 있다. 지난 답도 대화 실로 읽힌다.
- 구현 범위: `answers`에 `thread_id`/`parent_id`와 순서를 저장, `ask.build_prompt`에 앞 답을 자료로 넣는 follow-up kind, 지난 답 화면에 실 단위 표시와 "이어 묻기" 단추. 서버 `ask.py`·`store.py`, 화면 `web/app.js`. 대략 중간.
- 기존 구조와 맞음: `Store.add_answer`/`set_answer`/`get`/`list_answers`, `Asker` 큐와 `run_llm`, 기존 answers JSON과 지난 답 목록을 확장한다.

## I5 (S6 freebuff · T-423): 답 이어 묻기 (같은 답에 후속 질문)
- 근거: '할 일' 답을 받고 "그중 수요일 것만"을 물으려니 묻기 탭에서 종류·범위를 처음부터 다시 고르고 질문을 새로 써야 했다. 지난 답은 "녹취 2건", "녹취 16건"처럼 서로 무관한 항목으로만 쌓여 앞 답을 이어 쓸 방법이 없었다.
- 이득: 요약 → 파고들기 → 확인이 한 흐름으로 이어져, 같은 녹취를 다시 고르고 같은 맥락을 다시 설명하는 수고가 사라진다.
- 구현 범위: 서버 - `store.add_answer`에 `parent`(스레드 id) 필드, `ask.build_prompt`에 앞 답을 덧붙이는 인자, `/api/ask`가 `parent`를 받아 같은 ids로 다시 묻기(작음~중간). 화면 - 답 아래 '이어 묻기' 입력 한 줄, 지난 답을 스레드로 묶어 접기(중간). 저장 - answers JSON에 필드 하나 추가(옛 답은 `parent` 없음으로 읽기).
- 기존 구조와 맞음: Asker의 한 번에 하나 큐, `build_prompt`의 길이 초과 시 오래된 것부터 빼기, `list_answers`의 `about`, 지난 답 화면을 그대로 쓴다.

## I6 (S6 freebuff · T-423): 할 일 수집함 (녹취에서 뽑은 약속 체크리스트)
- 근거: '할 일'로 물으면 답이 글 덩어리로 답 화면과 지난 답에만 남는다. 체크할 수도, 기한만 모아 볼 수도 없고, 오늘·이번 주 할 일을 보려면 매번 범위를 골라 다시 물어야 했다. 할 일이 든 녹취가 16건에 흩어져 있어 결국 손으로 옮겨 적게 된다.
- 이득: 회의·통화에서 나온 약속이 한 목록에 쌓여 처리 여부를 눈으로 관리하고, 각 항목에서 출처 녹취를 열어 말한 맥락을 바로 확인한다.
- 구현 범위: 서버 - `voxlog/todos.py`(항목: text, due, source_id, done) + `data/todos/<id>.json` + `GET/POST/PATCH /api/todos`(작음~중간), 받아쓰기 완료나 '할 일' 답 생성 때 JSON으로 뽑아 저장(중간). 화면 - 네 번째 탭 '할 일'에 목록·체크·출처 링크(중간). 저장 - 새 폴더 하나만 늘고 meta/answers 형식은 그대로.
- 기존 구조와 맞음: `ask.KINDS["todo"]` 지시문과 `run_llm`, Store의 원자적 JSON 쓰기·id 정규식 규칙, 답의 `about`(첫 녹취 시각·제목) 표시 방식을 그대로 쓴다.
