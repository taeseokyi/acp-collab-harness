## 확정 (구현 순서대로)

### F1. 답의 출처 녹취 (I2) - 채택
- 까닭: 의견 둘 다 찬성. 저장 형식 변경 없이 읽기만 늘어 비용이 가장 작고, 여러 건 묶어 묻기의 신뢰를 바로 올림. F3 의 실 화면도 이것을 씀
- 정한 것(의견에서 받아들인 보완):
  - `sources` 는 답 JSON 에 **저장하지 않고 읽을 때 계산**(S6·S3) - 녹취 이름을 고치면(F2) 바로 따라감
  - 항목 `{id, title, label, recorded_at, status}`, 지워진 녹취는 빼고 `dropped` 수를 함께(S6). 녹취 이름은 F2 뒤로는 `label || title`
  - 단일 답(`GET /api/answers/<aid>`)은 전체, 목록(`GET /api/answers`)은 개수와 앞 3개만(S3)
  - 계산은 Store 도우미 하나를 두 경로가 함께 씀(S6)
  - 화면: 답 아래 출처 칩 3개 + '더 보기', 누르면 기존 `openDetail(id)`. 지워진 것이 있으면 '지워진 녹취 N건' 한 줄
- 하지 않는 것: 답 본문 안에 녹취 id 를 인용하게 하는 프롬프트 변경(S2 원안의 '필요하면') - 모델 출력에 기대는 것이라 뺌

### F2. 녹취 이름·태그 (I1 + I3 의 거르기) - 채택, 자동 제안은 보류
- 까닭: I1 은 찬성·조건부 찬성, I3 은 둘 다 'I1 과 합치는 조건'. 의견 셋이 모두 **I1 의 손으로 붙이는 `label`+`tags` 를 바탕**으로 하자고 함
- 정한 것:
  - meta 에 `label`(문자열, 없으면 빈 값)과 `tags`(배열). 자동 `title` 과 **분리** - 다시 받아쓰기가 `title` 을 덮어도 `label` 은 남음(store.py `set_transcript` 가 title 을 덮는 것은 그대로)
  - 옛 meta 는 `label=""`, `tags=[]` 로 채워 읽음(`location` 선례)
  - 쓰기 API 하나: `PATCH /api/recordings/<id>` 본문 `{label?, tags?}`. 서버 정규화 - label 40자, 태그 하나 20자·최대 10개, 앞뒤 공백 자르고 안쪽 공백 접기, 같은 태그 한 번(대소문자 무시 비교), 빈 태그 버림. 넘치면 400 과 까닭
  - Store 쓰기는 기존 `set_status`/`set_job` 과 같은 잠금 안 read-modify-write
  - 목록: `GET /api/recordings?tag=<태그>` 거르기(다른 거르기와 AND), `q` 는 label·tags 도 찾음
  - 묻기 범위가 태그 거르기를 따라감 - '지금 검색 결과' 범위는 `filterParams` 를 쓰므로 tag 를 넣으면 따라오고, '오늘'·'이번 주' 범위는 자체 from/to 를 만들므로(S6 지적) 태그를 적용할지 정해 적을 것 - **정함: 오늘·이번 주는 날짜 범위만(태그 무시), 태그로 묶어 묻기는 '지금 검색 결과' 범위로** 하고 화면에 그 뜻을 한 줄로 보임
  - 화면: 목록에 `label || title`, 태그 칩 2개 + `+N`(폰 320px 에서 넘치지 않게), 상세에 이름·태그 편집, 태그 칩을 누르면 그 태그로 거르기. 검색어가 이름·태그에만 맞은 경우 그 사실을 보임
  - 사용자 글은 `textContent` 로만 그림
- 보류: **I3 의 자동 태그 제안** - LLM 이 없으면 안 되고(`llm=false`), 한 번에 하나인 Asker 큐에 태우면 사용자 질문이 밀리고(S6), 글을 모델로 더 보내는 비용이 듦(S2). 손 태그가 쓰이는 것을 본 뒤 다시 정함

### F3. 답 이어 묻기 (I5 바탕 + I4 의 실 화면) - 채택
- 까닭: 이어 묻기는 두 슬롯이 따로 낸 같은 필요(I4·I5). 의견 넷 모두 찬성 또는 조건부 찬성, 셋이 **I5 의 `parent` 한 필드 설계가 낫다**고 함
- 정한 것:
  - 답 JSON 에 선택적 `parent`(부모 답 id) 하나. `thread_id`·`order` 는 두지 않음(순서는 `created`, 뿌리는 parent 를 따라감). 옛 답은 parent 없음 = 뿌리
  - `POST /api/ask` 에 선택적 `parent`. 서버가 **부모의 ids 를 그대로 씀**(클라이언트가 ids 를 보내면 무시하지 말고 400 - 뜻이 갈리지 않게). kind 는 `custom` 만(이어 묻기는 질문을 쓰는 것). 부모가 없으면 404, `done` 이 아니면 409
  - 프롬프트: `build_prompt(..., prev_answer=None)` 인자 하나(KINDS 늘리지 않음). 앞 답은 `<앞답>` 블록으로 감싸고 `_GUARD` 문장을 `<앞답>` 도 덮게 고침. 앞 답 길이 상한을 따로 두고(넘치면 앞 답 끝을 자름), 200k 초과 때 녹취를 빼는 규칙은 그대로. 넣는 앞 답은 **바로 위 부모 하나**(실 전체가 아님)
  - 부모의 녹취 일부가 지워졌으면 남은 것으로 묻고 답에 '녹취 N건 빠짐' 표시, 남은 것이 없으면 기존 400
  - 부모 답을 지우면 자식은 뿌리로 읽힘(parent 가 가리키는 답이 없으면 뿌리) - 지우기 규칙 바꾸지 않음
  - 화면: 펼친 답이 `done` 일 때만 '이어 묻기' 한 줄 입력(묻는 중엔 막힘). 지난 답은 실로 묶어 뿌리만 보이고 펼치면 이어진 답들. F1 의 출처 칩은 뿌리 답에만
- 재시작 때 running 답을 failed 로 바꾸는 규칙은 자식에도 그대로(S6 확인)
