## 눈여겨본 질문에 대한 답

- timeoutMs 를 안 쓰는 호출: 올리기(queue.js 의 fetch), 상세, 받아쓰기 기본값 읽기·저장(signal 만), health, answers, 묻기 폴링 모두 그대로다. timeoutMs 를 쓰는 곳은 app.js 1250(목록)·1681(묻기 POST) 뿐이고, api.js 는 timeoutMs 없으면 옛 판과 같은 길로 돈다(`if (!timeoutMs) return work`).
- 시간 제한과 늦은 응답이 겹칠 때: 약속이 한 번만 정착하므로 처리기 중복이 없다. 저장은 sttSave 표, 읽기는 `current()`+`seq`, 목록은 `listSeq`, 묻기는 `askToken` 이 늦은 응답을 막는다. 저장 시간 제한 뒤 늦게 온 성공 응답은 조용히 버려지고 칸은 사용자가 넣은 값 그대로이며, 다시 열면 새 GET 이 서버값으로 맞춘다(서버에 실제로 저장돼 있어도 화면 어긋남은 없다 - 값이 같으므로). R53-N10 과 같은 부류의 맞바꿈이라 지적하지 않는다.
- signal 과 timeoutMs 징검다리(바깥 signal 이 내부 컨트롤러를 끊음, 이미 끊겼으면 fetch 전에 끊음)는 바르게 짜였으나 지금 둘 다 쓰는 호출이 없다(방어 코드 - R57-N3).
- 목록 다시 시도·5초 폴링 겹침: loadList 머리에서 `listTimer` 정리, `listSeq` 판정으로 걸린 요청의 늦은 응답·오류 줄·aria-busy 가 모두 무시된다. 5초 폴링 중 오류가 계속되면 오류 줄을 매번 같은 글로 다시 그린다(`role="alert"` 중복 알림 가능성 - 관찰만, 토스트 반복은 옛 동작 그대로).
- '서버 오류' 연결 표시: 5xx 때 붉은 '서버 오류', 다시 시도 성공·업로드 뒤 목록 갱신(`n < prev → loadList`)·기록 탭 다시 열기로 '연결됨' 복귀를 화면으로 확인(장면 A). 다른 API 의 성공만으로는 복귀하지 않는데 이는 이전 동작과 같다.
- 상태 글: 새 녹음(b1~b3 '올렸습니다' 로 바뀜), 여러 녹음(b4 - 마지막 것만 따라가고 앞 것의 완료가 뒤 것의 글을 건드리지 않음), 오프라인(b5 '올리는 중' 유지 → 재연결 뒤 b6 '올렸습니다'), 영구 실패(c4 안내 나옴) 모두 화면으로 맞음. 다만 실패 안내 뒤의 갱신은 R57-N1 참조.
- 토스트 폭: 1280 → 560px 상한·가운데, 430 → 395.6px(92vw), 320 → 294.4px(92vw), 셋 다 화면 안. SCREEN-b D1 해소 확인.

## 지적

### R57-N1 (중) 영구 실패 안내 뒤에 다시 올려 성공해도 상태 글이 '올리지 못했습니다' 에 머문다

`applyRecUploadStatus` 가 실패 안내를 쓴 뒤 `state.recUpload` 를 null 로 비워(app.js:607) 이후 어떤 일이 벌어져도 이 글을 다시 쓸 길이 없다.

- 재현 1(사람 걸음): 400 영구 실패 → '마지막 녹음 … · 올리지 못했습니다 - 아래 "올리지 못한 녹음" 에서 다시 올릴 수 있습니다.' → '다시 올리기' 를 눌러 올림 성공(서버 2→3건, 상자에서 빠짐) → 상태 글은 그대로(c4·c5 갈무리). 안내가 가리키는 상자에 그 녹음이 이미 없다.
- 재현 2(백그라운드): 페이지가 400 으로 영구 실패로 표시한 녹음을 서비스 근로자의 Background Sync 가 물어 올려 성공하면, 상자는 사라지고 서버에 올라가 있건만 글은 '올리지 못했습니다 - 아래…' 로 남는다(c1 갈무리, 서버 2건 확인). 운영에서는 일시적 4xx 뒤에 나는 드문 길이다.
- 재현 3(코드로 확인): 실패 상자의 '지우기' 로 녹음을 버려도 같은 글이 남아 없는 상자를 가리킨다.
- 고치려면: 실패 안내를 쓴 뒤에도 추적을 유지해 대기열에서 빠지면 '올렸습니다' 로 바꾸거나, 재시도·지우기에서 글을 비우면 된다.

### R57-N2 (중) 새 검사가 T-512 의 실패 안내와 순서를 지키지 못한다

사보타주 표의 '안 잡힘' 중 83 관련 두 줄. ① 영구 실패 안내 가지를 통째로 지워도 83 이 통과한다 - T-512 가 만든 두 갈래(올렸습니다·올리지 못했습니다) 중 실패 갈래에 검사가 없다(동작 자체는 화면으로 확인, c4). ② clientId 잡기가 깨져 녹음을 멈추자마자 '올렸습니다' 로 바뀌어도(아직 올라가지 않았는데) 83 이 통과한다 - 기다림이 이른 값을 못 걸르고, 서버 도착 확인(`server_items==1`)은 별도 줄이라 순서와 무관하다. 고치려면 400 을 내는 실패 검사(상자·상태 글 확인)와 '올리는 중' → '올렸습니다' 순서 확인을 83 에 넣으면 된다.

### R57-N3 (하) 닿지 않는 길·기록만 할 것들

- 묻기 catch 의 token 가드를 지워도 어느 검사도 실패하지 않는다(방어 코드 - R55-N4 와 같은 부류).
- api.js 의 signal↔timeoutMs 징검다리는 지금 어느 호출도 함께 쓰지 않는 죽은 길이다. 방어로서는 바르다.
- sw.js 판번호가 21→24 로 세 칸 뛰었으나 캐시 갱신 목적상 문제 없고, 판번호를 지키는 검사는 원래 없다.

## playwright-cli 를 쓰다 막힌 것

- `eval` 은 식 하나만 받는다(SCREEN 문서와 같은 제약) - 모든 다문장 평가를 `(() => { …; return …; })()` 로 감쌌다.
- `window.fetch` 가로채기를 같은 캡처 변수로 두 번 겹치면, 두 번째 캡처가 첫 패치 함수를 물어 나중에 자기호출(RangeError)이 된다. 실제로 겪어 c2·c3 검사를 한 번 물고 갔다 - 겹치지 않게 매번 새 변수(`__pN`)로 캡처-패치-해제할 것. 재현 걸음은 `scenes.sh` 의 주석에 남겼다.
- 가로채기는 서비스 근로자의 올림을 막지 못한다(페이지의 window.fetch 만 바뀜). N1 재현 2 는 이 차이를 이용해 백그라운드 재올림을 관찰했다.

판정: 조건부 - R57-N1(상태 글이 사실과 어긋나 남는 것, T-512 가 고치려던 바로 그 증상의 실패 갈래 판)을 고치고, R57-N2 의 검사 보강을 권한다. T-508·T-511·T-512 의 주장된 동작 자체는 되돌려 보기와 화면에서 모두 제대로 동작했다.
