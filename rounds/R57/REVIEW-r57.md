## 지적

### R57-N1 (중) 묻는 도중 답을 지우면 '묻기' 단추가 잠긴 채 남는다 - 새 시간 제한 뒤에도 안 풀림
`ask()` 의 catch 가 `if (token !== state.askToken) return;` 을 단추 풀기 앞에 두게 됐다(옛 코드는 무조건 `ask-go.disabled=false`). `deleteAnswer` 는 화면에 펼친 답을 지우며 `state.askToken++` 만 하고 단추를 풀지 않는다. 재현: 답이 하나 펼쳐진 상태에서 묻기(응답 안 옴) → 같은 목록의 '지우기'(펼친 답) → 30초 제한이 지나도 `ask-go.disabled` 가 true, 안내 글도 없음(직접 확인: dis=true, status=''). 이 고침 전에는 실패하면 풀렸다. 성공 쪽 가드의 옛 문제를 실패·시간 제한 길까지 넓힌 셈이다. 풀려면 사람이 다른 답을 열거나 다시 불러야 한다. 고침 방향: 가드로 돌아가기 전에 단추를 풀거나, `deleteAnswer` 가 단추를 푼다.

### R57-N2 (중) 묻기 POST 가 시간 제한으로 끊겨도 서버에는 답이 만들어져 있을 수 있는데 알리지 않는다
`POST /api/ask` 는 202 를 즉시 돌려주는 구조(serve.py `_ask`)라 30초 제한은 넉넉하지만, 응답만 잃은 경우 서버에는 'running' 답이 이미 있다. 안내 글 '다시 묻기를 눌러 주세요' 를 따르면 같은 질문이 두 번 돌고(LLM 두 번), 시간 제한 뒤 `loadAnswers()` 를 부르지 않아 지난 답 목록에도 새 항목이 안 보인다. 안내 글에 '이미 만들어졌을 수 있음'을 쓰고 `loadAnswers()` 를 부르면 된다.

### R57-N3 (중) 검사가 지키지 못하는 곳 (검사 83)
위 표의 '통과 = 못 지킴' 줄: 영구 실패(4xx) 때의 '올리지 못했습니다 - 아래 …' 가지를 없애도 79~84 가 전부 통과한다. 오프라인 대기(waiting) 때 글 유지, 새 녹음 시작 때 추적 비우기, 저장 타임아웃 뒤 늦은 응답 무시(`currentSave`)도 안 지킨다(저장 요청은 abort 되어 늦은 응답이 오지 않으므로 사실상 닿지 않는 길). 가장 쓸모 있는 것은 업로드를 400 으로 막고 상태 글이 '올리지 못했습니다' 로 바뀌는지 보는 검사.

### R57-N4 (하) 저장 시간 제한 안내가 서버 저장 여부를 단정한다
PUT 이 서버에 닿아 저장됐는데 응답만 늦으면 '저장하지 못했습니다: 시간이 지났습니다' 로 알린다(abort 로 응답은 버려진다). 다시 열면 서버 값을 읽으므로 어긋남은 곧 풀리지만 한동안 사람이 잘못 본다. '저장됐는지 확인하려면 다시 열어 보세요' 정도로 순화.

### R57-N5 (하) '서버 오류' 표시가 돌아오는 때
`setConn('ok')` 는 목록 성공(과 health)에서만 부른다. 목록이 5xx 였다가 사람이 묻기·상세·업로드에 성공해도 연결 표시는 '서버 오류' 로 남고, 바쁜 항목이 없으면 자동 재시도도 없다(`wasBusy` 일 때만 5초 폴링). 목록 탭을 다시 열거나 '다시 시도' 를 눌러야 돌아온다. 위험은 없고 문구가 낡을 뿐.

### R57-N6 (하) 올림·다시 시도의 사소한 겹침
- `api.js`: 바깥 `signal` 에 붙인 abort 리스너를 거두지 않는다(지금 timeoutMs 와 signal 을 함께 쓰는 호출은 없어 닿지 않음). 본문 읽기 도중 바깥이 끊으면 날 AbortError 가 나가는 것은 옛 동작 그대로.
- `timeoutMs` 를 안 쓰는 호출(올리기·상세·받아쓰기 기본값·묻기 폴링)은 `if (!timeoutMs) return work;` 로 옛 경로 그대로라 바뀌지 않음(코드로 확인).
- 목록 재시도·5초 폴링 겹침은 `listSeq` 가 막아 낡은 응답이 칸을 건드리지 않음(오류 줄·aria-busy 모두 현재 순번만).
