## [REV 101 / 2026-09-28 내림] 8.5 냉시작 - 슬롯을 닫고 다시 열 때

사유: ACP 시절 절차. `/acp spawn --thread auto` 는 막힌 경로이고 `fleet.py open`/`prepare` 는 폐기. 살린 두 줄은 `8.0` 으로 흡수했다.

### 8.5 냉시작 - 슬롯을 닫고 다시 열 때

> **2026-09-28 대체됨 (`8.0`).** 아래는 ACP 슬롯 시절의 절차로 남깁니다.
> 지금은 관리자가 네이티브 상주 슬롯을 직접 열고, 슬롯이 죽으면 같은 슬롯 ID 로 새로
> 열어 명부 세션키만 교체합니다. `fleet.py open`/`prepare` 는 폐기된 그대로입니다.

**세션이 끊기면 잃는 것과 남는 것이 갈립니다.** 남는 것은 이 파일과 아카이브뿐입니다.

**닫기 전 (관리자):**

- 진행 중 태스크가 있으면 보드 상태를 `TODO` 로 되돌립니다. `IN-PROGRESS` 인 채로 닫으면
  다음 작업자가 없는 선행 결과를 찾습니다 (`8.3`)
- 아웃박스의 완료 블록을 아카이브로 옮기고, 결론을 `4절` 에 남깁니다
- 미커밋을 정리합니다. 작업자의 git 앵커는 HEAD 가 최신일 때만 쓸모가 있습니다

**다시 열 때 (순서대로):**

1. `/acp spawn ... --thread auto` 로 지속 세션을 엽니다 (`8.2`). 채널 루트에서도 됩니다
2. `2. 세션 명부` 의 **세션키를 새 값으로 갱신**합니다. 슬롯 ID 와 확인토큰은 그대로 씁니다 -
   슬롯은 자리 이름이지 세션이 아닙니다
3. 세션 스토어의 `label` 을 채웁니다 (`8.4`). `/acp spawn --label` 로는 안 들어갑니다
4. **태석님이 그 대화에 위임 한 줄을 칩니다**(`0절`). 관리자가 대신 전달할 수 없습니다(REV 58)
5. 첫 지시에 **슬롯 ID / 확인토큰 / REV** 를 적습니다. 작업자는 자기 세션키를 모릅니다

**1~2~3 과 5 의 값은 `tools/fleet.py` 가 만들어 줍니다.**

```bash
python3 tools/fleet.py close                 # 닫기 전 점검
python3 tools/fleet.py open --slot S3 --session-key agent:claude:acp:...
python3 tools/fleet.py status                # REV / 슬롯 / 열린 태스크 / 미커밋
```

`open` 이 명부 세션키를 갱신하고 세션 라벨을 주입한 뒤, 태석님이 치실 위임 한 줄과
첫 지시에 넣을 값을 현재 REV 로 찍어 줍니다. 사람이 옮겨 적는 단계를 없애는 것이 목적입니다.

**"AIMEM.md 를 읽어라"는 더 이상 적지 않아도 됩니다.** `CLAUDE.md` 가 자동 주입되고
(`7절` 실측) 거기서 `AIMEM.md` 를 가리킵니다. 작업자는 첫 턴에 스스로 대조를 시작합니다.

## [REV 101 / 2026-09-28 내림] 8.1 하네스 선택 + 8.2 세션 수명

사유: 둘 다 ACP 전제. `8.1` 은 opencode ACP 어댑터 선택 정책으로 네이티브 슬롯에는 적용되지 않는다. `8.2` 는 이미 "대체됨" 배너가 있던 ACP 세션 수명 실측이다. 운영 채널 한 줄만 `0.7` 로 살렸다.

### 8.1 하네스 선택 - claude 기본, opencode 는 재시험 후 복귀

opencode 를 쓰는 이유는 **토큰 비용 절감**입니다(태석님). 품질 우위가 아닙니다.
그래서 살아 있으면 쓰고, 죽어 있으면 미련 없이 claude 로 갑니다.

- opencode 모델 설정 (실측 2026-08-25 15:15): `~/.config/opencode/opencode.jsonc` 의
  `model` / `small_model` 둘 다 `opencode/x-preview-f-free`.
  `~/.openclaw/openclaw.json` 의 `opencode` 프로바이더에 등록된 모델도 **이 하나뿐**입니다
  (`baseUrl: https://opencode.ai/zen/v1`, 별칭 `opencode-ox`).
  즉 **대체 모델이 없습니다.** 이 엔드포인트가 죽으면 opencode 하네스 전체가 죽습니다
- **`ACP_TURN_FAILED ... Endpoint is unavailable` 은 업스트림 무료 티어 장애입니다.**
  작업자 잘못도 규약 위반도 아니므로 준수 판정에 넣지 않습니다.
  판별: `journalctl --user -u openclaw-gateway | grep ACP_TURN_FAILED`
- **현재 정책 (2026-08-25 15:18 전환): 실작업은 claude 로 배정한다.**
  opencode 는 **하루 첫 태스크 전에 헬스 프로브 1회**만 태우고, 성공하면 그날은
  opencode 우선으로 복귀한다. 실패하면 그날은 claude 로만 간다 - 재시도를 쌓지 않는다
  (실패해도 토큰 0 이라 프로브 자체는 공짜지만, 실작업을 태우면 대기 시간이 낭비된다)
- 한 태스크에서 opencode 가 **2회 연속 UNAVAILABLE 이면 즉시 claude 로 재배정**한다
- 실측 이력: 14:26 실패 -> 14:38 성공 -> 15:12 실패(헬스 프로브, 산출물 0/토큰 0).
  오늘 3회 중 2회 실패. **간헐적이지만 신뢰할 수 없는 수준**

### 8.2 세션 수명 - 지속 세션은 스레드 채널에서만

> **2026-09-28 대체됨 (`8.0`).** 아래는 ACP 시절의 실측 기록으로 남깁니다.
> 지금은 ACP 를 쓰지 않고 네이티브 상주 슬롯을 엽니다. 스레드 바인딩도 필요 없습니다.

- `mode="run"` 은 한 턴 뒤 어댑터가 내려간다. 재접촉 불가 - 다음 태스크는 새 스폰
- `mode="session"` 지속 세션은 **채널 스레드 바인딩이 있어야** 한다.
  DM 에서 시도하면 `thread_required` 로 거부된다 (실측 2026-08-25 15:11)
- 따라서 지금의 DM 운영에서는 **지속 세션이 없다.** 연속성은 세션이 아니라 **이 파일**이 맡는다.
  각 작업자는 매번 이 파일을 읽고 시작한다 - 그만큼 토큰을 더 쓴다. 이것이 지속 세션 부재의 비용
- 지속 세션이 필요하면 스레드가 되는 채널(디스코드 서버 채널 등)로 운영을 옮겨야 한다
- **운영 채널 (2026-08-25 16:07 개설):** 디스코드 `#sss-fleet`
  (guild `1467406994640998463` / channel `1541705515908988989`).
  coding 계정 허용 목록에 등재 완료(핫 리로드, 재시작 불필요).
- **정정 (2026-09-11 실측):** "이 채널에서 스폰하면 지속 세션이 열린다"는 **틀렸다.**
  `sessions_spawn(mode="session", thread=true)` 이 `thread_binding_invalid` 로 거부된다.
  원인은 `prepareAcpThreadBinding` 의 마지막 단계 `resolveConversationRefForThreadBinding` -
  디스코드 플러그인의 `resolveInboundConversation` 은 **이미 스레드 안에 있는 세션**에만
  conversationId 를 내주고, 채널 루트 세션에는 null 을 준다. 채널 정책/어댑터/placement
  검사는 모두 통과하므로 설정 문제가 아니다
- **채널을 만든 것만으로는 부족하다.** 스폰을 거는 세션 자체가 스레드에 붙어 있어야 한다
- **검증 완료 (2026-09-11 10:03): `/acp spawn ... --thread auto` 로 지속 세션이 열린다.**
  가설대로였다. 이 경로는 저장된 세션 origin 이 아니라 **들어온 메시지**에서 바인딩
  컨텍스트를 뽑으므로(`resolveAcpCommandBindingContext`) 채널 루트에서도 성립한다.
  - 열린 세션: `agent:claude:acp:f5eb2255-78a7-41e8-a140-d7125f69b77b` (S1)
  - `sessions_send` 로 **두 턴 연속 재접촉 성공.** `mode="run"` 에서 계속 나던
    `Agent "claude" no longer exists in configuration` 이 나오지 않는다
  - 턴 종료 후에도 세션이 `sessions_list` 에 남는다(`status: done`, 삭제되지 않음).
    `mode="run"` 은 기록까지 사라졌다 - 이것이 결정적 차이
  - **대화 기억이 턴을 넘어 유지된다.** 2턴째에 "파일 읽지 말고 기억만으로 답하라"고
    물었더니 직전 턴의 REV/토큰/cwd 를 그대로 복원했다
- **따라서 연속성 비용이 사라진다.** 지속 슬롯에서는 작업자가 매 턴 이 파일을 통째로
  다시 읽지 않아도 된다. 다만 `/acp spawn` 은 소유자 전용이라 **슬롯 개설은 태석님만**
  할 수 있고, 개설 후 운전(`sessions_send`)은 관리자가 한다

- **자가 스폰 실측 (2026-09-11 10:12~10:21): 관리자가 직접 띄운 ACP 세션은 "기억 없는 슬롯"이다.**
  `sessions_spawn` 으로 띄운 프로브(`agent:claude:acp:ad5b52be-...`, 라벨 `probe-thread-selftest`)
  로 4턴을 왕복했다. 결과가 갈렸다.
  - 재접촉: **된다.** 4턴 전부 응답. `sessions_list` 에도 남는다
  - 기억: **안 된다.** 1턴에 `PROBE-OK`, 2턴에 `PROBE-2-OK` 를 답하게 한 뒤 3턴에
    물으니 "이 세션에서 처음 보는 메시지"라고 답했다. 토큰(`MEM-7Q4X`)을 외우게 한
    직후 턴에도 "받은 기록이 없다"고 했다. 트랜스크립트 파일에는 5턴이 전부 남아 있으나
    **어댑터가 그것을 다시 먹이지 않는다** - 기록은 되고 재생은 안 된다
  - 대조군 S1(`f5eb2255-...`, 태석님이 `/acp spawn --thread auto` 로 개설):
    같은 시험에서 `MEM-S1-8K2P` 를 정확히 복원했다. **기억이 유지된다**
  - **결론: 재접촉 가능 != 지속 세션.** 진짜 지속 슬롯은 `/acp spawn --thread auto`
    (소유자 전용) 로만 만들어진다. 관리자 자가 스폰은 한 턴짜리 일회용으로만 쓴다 -
    여러 턴이 필요한 일을 맡기면 매 턴 백지에서 시작하므로 조용히 틀린 답을 낸다

## [REV 101 / 2026-09-28 내림] 8.4 슬롯 식별 - 세션 라벨

사유: 본문이 `/acp spawn --label` 이 세션 스토어 `label` 에 안 들어가는 ACP 버그 대응이다. 네이티브 `sessions_spawn(label:...)` 은 정상 반영되므로 사문화. 원칙 한 줄만 `8.1`(구 `8.3`)로 살렸다.

### 8.4 슬롯 식별 - 세션 라벨을 반드시 붙인다

**`/acp spawn --label` 은 ACP 기록에만 남고 세션 스토어의 `label` 필드에는 들어가지
않습니다** (실측 2026-09-11 10:30). 그 결과 Control UI 세션 목록에서 슬롯 셋이 전부
`Assistant (acp)` 로 똑같이 보여 구분할 수 없었습니다. `sessions_spawn` 으로 띄운
세션은 라벨이 정상으로 붙으므로, 차이는 `/acp` 경로에 있습니다.

- 조치: `~/.openclaw/agents/claude/sessions/sessions.json` 의 해당 세션키 항목에
  `label` 을 직접 넣으면 즉시 반영됩니다(게이트웨이 재시작 불필요, 실측 확인).
  현재 `aimem-S1` / `aimem-S2` / `aimem-S3` 로 지정돼 있습니다
- **관리자는 슬롯을 새로 열 때마다 이 라벨을 확인하고, 비어 있으면 채웁니다.**
  라벨이 없으면 UI 에서 슬롯을 구분할 수 없고, 잘못된 슬롯에 지시가 갈 위험이 생깁니다
- 라벨은 편의 장치일 뿐입니다. **안정 식별자는 여전히 세션키이고**, 대조는
  `2. 세션 명부`의 세션키 + 확인토큰으로 합니다

사유: 인바운드 참조 0건. 4단계 표의 실질은 `8.0-2`(의사결정과 실행의 분리)로 대체됐다.

### 1.5 진행 단계 (태석님 확정 2026-09-11)

일은 네 단계로 진행합니다. **단계마다 담당자가 따로 있는 것이 아니라, 한 단계 안에서
각자가 자기 입장으로 참여합니다.** 한 사람이 한 단계를 독점하면 그 사람의 사각지대가
그대로 결과가 됩니다.

| 단계 | 태석님 | 관리자(클로) | 작업자 슬롯 |
| ---- | ------ | ------------ | ----------- |
| 1 구체화 | 무엇을 왜 원하는지 말한다. 최종 확정 | 목표·산출물·완료조건·범위밖 초안을 `1절`에 쓴다 | **반론 담당** 한 슬롯이 전제를 친다. 목표가 틀렸으면 여기서 말한다 |
| 2 설계 쪼개기 | 쪼갠 결과를 보고 방향만 판정 | 태스크 분해 + 소유권 배분 초안 | 자기 몫을 되받는다 - 이대로 되는가, 더 나은 경계가 있는가 |
| 3 개발 | 보기만 한다 | 브리프 발송, 막힌 것 해소 | 소유 경로 안에서 구현하고 인계 노트를 채운다 |
