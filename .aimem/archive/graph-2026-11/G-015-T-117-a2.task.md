# T-117 `browser_ui.py` - 보기 설정과 접근성 목표의 검사 구멍 메우기

## 고칠 파일 (이 하나뿐입니다)

`projects/웹워들/tests/browser_ui.py`. **검사를 더하기만** 합니다. 바로 앞 태스크(T-116)가
같은 파일에 통계 시나리오 셋을 더해 두었으니 **그것도 건드리지 마십시오.**
앱(`web/` 아래)과 다른 테스트 파일은 남의 것입니다.

## 왜 - 두 목표가 아직 참·거짓을 못 가립니다

- **보기 설정**: `scenario_settings` 는 색약 모드에서 `correct` 가 주황인 것만 봅니다.
  **`present` 가 파랑인지는 아무도 안 봅니다.** 새로 고침 뒤 유지되는지는 `<html>` 속성으로만 보고
  **실제로 칠해진 색**으로는 안 봅니다
- **접근성**: 대비를 **판정된 타일 세 가지(correct/present/absent)** 에서만, 그것도
  밝음·어두움·색약 **따로따로만** 잽니다. **어두움+색약을 겹친 경우**는 안 잽니다.
  **화면 키·입력 중 칸·토스트·본문 글자**는 아예 안 잽니다

## 알아야 할 것 (확인된 사실)

- 테마는 `<html>` 의 `data-theme="light|dark"` 와 `data-colorblind="on|off"` 입니다.
  **둘은 서로 독립이라 겹칠 수 있습니다**(어두움+색약)
- 설정 창의 체크상자는 `#set-dark` · `#set-cb` · `#set-hard`. `open_settings` / `close_modal` 도우미가
  이미 있습니다
- 이 파일에는 `parse_rgb`, `luminance`, `contrast`, `tile_colors`, `check_contrast`, `probe_locations`
  도우미가 **이미 있습니다. 새로 만들지 말고 그대로 쓰십시오**
- `getComputedStyle` 로 실제 색을 물으십시오. CSS 변수 이름이나 class 를 보는 것은 증거가 아닙니다

## 더할 것 1 - 보기 설정 (목표 이름 `"설정"`)

새 시나리오를 더하거나 `scenario_settings` **뒤에 새 시나리오**로 넣으십시오.

1. 오늘의 정답에 대해 `probe_locations(page, answer)` 로 **`present` 판정이 나오는 추측과 그 자리**를
   구합니다(이미 있는 도우미입니다). 그 추측을 제출해 `present` 타일을 하나 만듭니다
2. 설정에서 `#set-cb` 를 켭니다
3. 그 `present` 타일의 **배경색을 `tile_colors` 로 읽어** 파랑 계열인지 봅니다:
   `b > g > r` 이어야 합니다 (실제 값은 `rgb(133, 192, 249)`). `detail` 에 rgb 를 그대로 찍으십시오
4. 같은 방법으로 색약 `correct` 가 주황(`r > g > b`)인지도 **같은 판에서** 봅니다
   (지금은 다른 시나리오에서 따로 봅니다 - 한 화면에서 둘이 **서로 다른 색**인 것까지 봐야
   색약 모드가 제구실을 합니다). `correct` 배경 ≠ `present` 배경 도 확인하십시오
5. **새로 고친 뒤에도 색이 그대로인지** - `page.reload()` 하고 같은 두 타일의 배경색이
   새로 고치기 전과 **같은 rgb** 인지 봅니다. 속성(`data-colorblind`)만이 아니라 **칠해진 색**입니다
6. `shot(page, "theme-colorblind-present")`

## 더할 것 2 - 접근성 대비 (목표 이름 `"접근성"`)

**네 모드 전부**에서 잽니다: `밝음` · `어두움` · `색약` · **`어두움+색약`**.
모드를 바꿀 때마다 아래 목록을 전부 재고, 각각 **4.5:1 이상**이어야 합니다.
검사 이름에 무엇을 어느 모드에서 쟀는지 넣고(`접근성 - 대비 <무엇> <모드>`),
`detail` 에 `비 X.XX:1 (fg=…, bg=…)` 를 반드시 찍으십시오.

재는 것 (전부 `getComputedStyle` 의 `color` 대 `backgroundColor`):

1. **판정 타일 셋** - `correct` · `present` · `absent` (이미 `check_contrast` 가 합니다.
   네 번째 모드만 추가하면 됩니다)
2. **입력 중 칸** - 아직 판정 전인 `data-state="filled"` 타일의 글자색 대 **실제로 뒤에 깔린 색**.
   타일 배경은 투명(`rgba(0, 0, 0, 0)`)이라 그대로 쓰면 안 됩니다 -
   **`document.body` 의 `backgroundColor`** 를 배경으로 쓰십시오
3. **화면 키 네 가지** - 아무 판정도 없는 글자 키 하나, 그리고 `data-state` 가
   `correct` · `present` · `absent` 인 키 하나씩 (`#keyboard .key[data-key="x"]`).
   판을 한두 줄 둬서 세 상태가 모두 나오게 하십시오 (`probe_locations` 를 쓰면 한 줄로 만들 수 있습니다)
4. **화면의 `ENTER` 와 `⌫` 키** - `#keyboard .key[data-key="enter"]` · `[data-key="back"]`
5. **토스트** - 토스트가 떠 있는 동안 `#toasts .toast` 의 글자색 대 배경색
   (없는 단어를 쳐서 띄우면 됩니다: `page.keyboard.type("zzzzz")` + Enter)
6. **본문 글자 두 가지** - 머리글 제목 `.header h1`, 그리고 통계 창의 작은 설명 글
   `#stat-row .stat span` (배경은 각각 `body` 와 `.modal-box` 의 계산된 배경색)

타일·키 배경이 투명으로 나오면 **뒤에 깔린 요소의 색**을 찾아 쓰십시오 - `rgba(0, 0, 0, 0)` 을
그대로 넣어 계산하면 거짓 결과가 나옵니다.

**빈 칸의 테두리 대비**는 이번 범위가 아닙니다. 다만 밝은 테마에서
`.tile[data-state="empty"]` 의 `borderColor` 대 `body` 배경 비를 **한 번 재어 보고에만 적으십시오**
(검사로 만들지 마십시오).

## 더할 것 3 - 키보드만으로 완주 · `aria-live` (목표 이름 `"접근성"`)

`scenario_accessibility` 가 이미 물리 키보드로 완주합니다. 거기에 더합니다.

1. **마우스 없이 화면 키만으로 한 줄 제출** - `tab_key(page, "...")` 도우미로 글자 키에 포커스를 옮겨
   `Enter` 로 글자를 다섯 개 넣고, 그다음 `tab_key(page, "enter")` 로 ENTER 키에 가서 `Enter` 를 눌러
   **제출이 되는지** 봅니다 (줄 판정이 끝나는지 `wait_submit_settled`). 지금은 ENTER 키에
   포커스가 가는 것까지만 보고 **눌러 보지는 않습니다**
2. **`aria-live` 로 결과가 읽히는지** - `#toasts` 가 `aria-live="polite"` 인 것은 이미 봅니다. 더해서
   - **진 판**에서 `정답: XXXXX` 글이 그 `aria-live` 영역 안에 **실제로 들어가는지**
     (`#toasts .toast` 의 글이 `정답: ` 로 시작하고 정답 다섯 글자 대문자를 담는지)
   - 판정된 타일의 `aria-label` 에 글자와 판정말(`맞음`/`자리 틀림`/`없음`)이 함께 들어가는지
     (`STATE_LABEL` 이 이미 파일에 있습니다)
   - 보드가 `role="grid"`, 키보드가 `role="group"` 이고 둘 다 `aria-label` 이 비어 있지 않은지
